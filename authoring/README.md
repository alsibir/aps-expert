# Исходные материалы сайта АПС

## 1. Назначение

Каталог `authoring/` предназначен для хранения исходных материалов, используемых при подготовке публикаций, портфолио, редактируемых документов и графических материалов сайта АПС.

Репозиторий: https://github.com/alsibir/aps-expert  
Опубликованный сайт: https://alsibir.github.io/aps-expert/

**Важно:** репозиторий GitHub является публичным. Размещение файла в `authoring/` не публикует его в интерфейсе сайта автоматически, но делает файл доступным посетителям публичного репозитория и через историю Git. Не следует считать `drafts/` или `revisions/` закрытыми каталогами.

## 2. Структура

```text
authoring/
├── docx/
│   ├── alpha/             # Редактируемые документы проекта АЛЬФА
│   ├── aliot/             # Редактируемые документы проекта ALIOT
│   └── articles/          # Редактируемые оригиналы статей
├── drafts/
│   ├── publications/      # Не опубликованные на сайте статьи и материалы
│   └── portfolio/         # Черновики описаний проектов и работ
├── diagrams/
│   ├── plantuml/          # Исходники PlantUML, не участвующие в сборке
│   └── mermaid/           # Исходники Mermaid, не участвующие в сборке
├── revisions/             # Промежуточные редакции, согласования и версии
├── references/            # Разрешённые к открытому хранению источники
└── README.md              # Настоящие правила
```

Файлы `.gitkeep` сохраняют незаполненные каталоги в системе контроля версий. После добавления содержимого файлы `.gitkeep` можно удалить.

## 3. Размещение и назначение файлов

| Каталог | Состав и правила размещения |
| --- | --- |
| `docx/alpha/` | Исходные редактируемые документы проекта «АЛЬФА» в формате DOCX, разрешённые для публичного размещения. |
| `docx/aliot/` | Исходные редактируемые документы ALIOT в формате DOCX, прошедшие проверку на допустимость раскрытия. |
| `docx/articles/` | Редактируемые оригиналы авторских статей, в том числе материалы до преобразования в Markdown/MDX. |
| `drafts/publications/` | Подготовленные и находящиеся на редактировании статьи. Файлы здесь не становятся страницами сайта автоматически. |
| `drafts/portfolio/` | Подготовительные описания проектов, карточек портфолио и сопроводительных материалов. |
| `diagrams/plantuml/` | Тексты схем PlantUML (обычно `.puml`), не подключённые к автоматической сборке. |
| `diagrams/mermaid/` | Тексты схем Mermaid (обычно `.mmd` или `.md`), не подключённые к автоматической сборке. |
| `revisions/` | Промежуточные редакции, результаты согласований и снимки версий, когда одной истории Git недостаточно. |
| `references/` | Справочные материалы, общедоступные выдержки и перечни первоисточников с реквизитами и ссылками. |

Каталог `authoring/` не заменяет существующие `src/`, `public/` и корневой `diagrams/`. Перемещение действующих исходников и опубликованных файлов без проверки зависимостей не допускается.

## 4. Связь с опубликованным сайтом

| Область репозитория | Назначение |
| --- | --- |
| `authoring/` | Рабочие первоисточники и вспомогательные материалы. Автоматически не включаются в публикацию. |
| `src/content/docs/` | Тексты страниц Starlight (Markdown/MDX), участвующие в сборке сайта. |
| `src/` | Компоненты, стили, данные, конфигурация и другие исходные файлы приложения. |
| `public/` | Статические ресурсы, которые копируются в опубликованный сайт: PDF, изображения, загружаемые файлы и другие доступные посетителям материалы. |
| `diagrams/` в корне | Существующие проектные исходники схем; правила их использования определяются текущими скриптами и процессом сборки. |
| `dist/` | Генерируемый результат сборки. Ручное редактирование не допускается. |

Путь `authoring/diagrams/` предназначен только для схем, **не требуемых текущей сборке**. Если схема должна отображаться на сайте, необходимо разместить её сгенерированное изображение в предусмотренном каталоге `public/` или подключить отдельную процедуру сборки и проверить ссылки.

## 5. Порядок подготовки и публикации

1. Поместить разрешённый к публичному хранению исходный документ в соответствующий каталог `docx/`, `drafts/`, `diagrams/` или `references/`.
2. Проверить полноту содержания, корректность терминов, обозначений, ссылок, рисунков и реквизитов нормативных документов.
3. Проверить право на публикацию, удалить конфиденциальные сведения и персональные данные, не предназначенные для публичного доступа. Для материалов по заказным проектам использовать согласованные либо обезличенные демонстрационные версии.
4. Подготовить итоговый текст страницы в Markdown/MDX и разместить его в `src/content/docs/` с учётом существующей навигации, структуры и оформления сайта.
5. Если требуется просмотр или загрузка PDF, DOCX, архивов или изображений посетителями сайта, разместить специально подготовленные публичные копии в `public/`. Не создавать ссылки на `authoring/` как на путь внутри опубликованного сайта.
6. Проверить отображение рисунков и диаграмм, корректность относительных ссылок и навигации на компьютере и мобильном устройстве.
7. Выполнить проверку сборки командами `npm run build`, `python3 scripts/audit.py` и `python3 scripts/audit-anchors.py`. При наличии схем, обрабатываемых при развёртывании, также выполнить предусмотренные проектом команды их генерации.
8. Зафиксировать изменения в Git, выполнить проверку через отдельную ветку и запрос на включение изменений (pull request). После слияния убедиться в успешном выполнении публикационного процесса GitHub Actions.

**Принцип:** наличие исходника в GitHub и наличие страницы на опубликованном сайте — два различных состояния. Материал считается опубликованным на сайте после успешной сборки и появления соответствующей страницы или ресурса по рабочему адресу.

## 6. Именование и управление редакциями

- Для новых технических имён файлов рекомендуется использовать строчные латинские буквы, цифры и дефисы: `alpha-system-description-v1.0.docx`, `requirements-traceability.puml`, `document-automation-draft.md`.
- Для документов, которым присвоено обозначение по ГОСТ или в рамках проекта, сохранять установленное обозначение в документе. Имя файла должно позволять однозначно определить проект, вид документа и редакцию.
- Редакции отмечать предсказуемо, например `v1.0`, `v1.1`, `v2.0`; при необходимости указывать дату в формате `ГГГГ-ММ-ДД`.
- Актуальная редакция должна однозначно определяться. Не использовать цепочки неопределённых суффиксов `final`, `final2`, `new+` и аналогичные обозначения.
- Не создавать бессистемные копии при каждом изменении: для обычных изменений использовать историю Git, а `revisions/` — для существенных контрольных редакций или материалов согласования.
- Для текстов применять кодировку UTF-8. Исходные файлы схем сохранять отдельно от сгенерированных SVG/PNG/PDF.

## 7. Ограничения публичного размещения

Запрещается добавлять в данный каталог пароли, ключи, токены, сертификаты с закрытыми ключами, внутренние переписки, персональные данные третьих лиц, закрытые технические материалы и документы, распространение которых ограничено договором или иными обязательствами.

Перед добавлением DOCX, PDF и изображений необходимо проверить не только видимое содержимое, но и свойства файлов, встроенные объекты, примечания, исправления, историю рецензирования и метаданные. Если документ не прошёл проверку, он должен храниться **вне публичного репозитория**. Файл `.gitignore` не обеспечивает конфиденциальность уже опубликованных в истории Git данных.

Справочные нормативные материалы следует размещать с учётом лицензионных и авторских ограничений. Предпочтительны библиографические ссылки, реквизиты документов и разрешённые к распространению выдержки.

## 8. Сопровождение

При создании нового вида материалов допускается расширить структуру `authoring/`, предварительно зафиксировав назначение нового каталога в настоящем файле. Опубликованные страницы, ссылки и существующие исходники сайта изменяются только в рамках отдельной проверенной задачи.
