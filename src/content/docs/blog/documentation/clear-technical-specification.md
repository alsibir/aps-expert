Идеальное техническое задание позволяет Заказчику, Разработчику и специалисту по испытаниям одинаково понять ожидаемый результат. По нему можно оценить объём работ, реализовать согласованные функции и проверить их выполнение. Сам по себе подробный текст такого результата не обеспечивает: нужны исходные данные, решения по спорным вопросам и измеримые условия приёмки.

Ниже приведён порядок подготовки ТЗ для программного обеспечения и автоматизированной системы. Он подходит для разработки нового продукта и изменения существующего. Структуру и глубину описания следует выбирать с учётом масштаба работ и требований проекта.

**Начать следует с трёх вопросов:** какой результат требуется получить, что входит в текущую поставку и каким способом будет подтверждена готовность. Если ответы отсутствуют, сначала необходимо собрать исходные данные.

## 1. Определить задачу и ожидаемый результат

Фраза «автоматизировать обработку обращений» задаёт направление, но не объясняет, какую проблему требуется решить. Полезнее описать существующий процесс, его затруднения и желаемое изменение.

Для демонстрационной АС «АЛЬФА» исходная ситуация может выглядеть так: обращения поступают по разным каналам, ответственный назначается вручную, история рассмотрения хранится разрозненно. Ожидаемый результат — единая регистрация обращений с идентификатором, ответственным, статусом и историей действий.

| Вопрос | Что зафиксировать |
| --- | --- |
| Кто использует результат? | Роли пользователей и выполняемые ими задачи |
| Какая проблема решается? | Наблюдаемое затруднение действующего процесса |
| Как изменится работа? | Будущий порядок действий и границы автоматизации |
| Как оценить пользу? | Показатель, исходное значение, целевое значение и способ измерения |
| Кто принимает решения? | Владелец процесса и уполномоченные согласующие |

Показатель пользы и технический критерий приёмки могут различаться. Сокращение времени обработки обращения зависит также от организации работы сотрудников. Возможность зарегистрировать обращение и сохранить историю действий проверяется непосредственно в системе.

## 2. Собрать исходные данные и обозначить неизвестное

До написания требований следует получить описание процесса, примеры входных и выходных данных, ограничения среды, сведения об интеграциях и составе поставки. Для существующей системы дополнительно нужны актуальные версии, интерфейсы и ограничения совместимости.

| Исходные сведения | Зачем нужны |
| --- | --- |
| Роли, полномочия и согласования | Для определения разрешённых действий |
| Формы, справочники и примеры документов | Для описания полей, форматов и результатов |
| Перечень внешних систем | Для определения взаимодействий и зависимостей |
| Конфигурация среды | Для проверки совместимости и производительности |
| Условия эксплуатации и поддержки | Для описания сопровождения, восстановления и передачи результата |

Неизвестные значения нельзя превращать в придуманные требования. Их следует занести в журнал вопросов: идентификатор, вопрос, влияние на работу, ответственный и срок решения. Если неизвестен протокол интеграции, нельзя считать согласованными её трудоёмкость и критерии проверки.

Для проведения интервью доступен [перечень вопросов установочной встречи](/alsibir-expert/blog/analytics/project-discovery-ai/).

## 3. Ограничить состав работ

ТЗ должно позволять отличить текущую поставку от дальнейшего развития. Для каждого спорного элемента следует определить, включён ли он в работу, отложен или требует отдельного решения.

| Элемент демонстрационного проекта | Граница текущей поставки |
| --- | --- |
| Обращения | Регистрация через веб-интерфейс |
| Уведомления | События и получатели согласуются в отдельной таблице |
| Импорт старых данных | Не включён; возможен после обследования источника |
| Мобильное приложение | Не включено; требования к браузеру телефона рассматриваются отдельно |
| Внешняя почтовая служба | Условия подключения предоставляет Заказчик |

Исключение из объёма следует формулировать конкретно. Запись «интеграции не предусмотрены» противоречит требованию отправлять сообщения через внешнюю службу, если такое взаимодействие не описано отдельно.

## 4. Составить структуру ТЗ

Ниже приведена рабочая схема содержания. Она не является универсальной нормативной формой: состав разделов уточняется для конкретного объекта и установленного порядка документирования.

| Раздел | Что должно быть понятно читателю |
| --- | --- |
| Основания, назначение и цели | Почему выполняется работа и какой результат ожидается |
| Объект и границы | Какие процессы, пользователи и компоненты охвачены |
| Термины и исходные данные | Как понимать специальные понятия и на какие сведения опираться |
| Функции и сценарии | Что выполняет система и как обрабатывает исключения |
| Данные и интерфейсы | Какие сведения поступают, хранятся и передаются |
| Характеристики качества | Какие условия производительности, доступности и защиты требуется проверить |
| Ограничения среды | Где и при каких условиях должен работать результат |
| Состав работ и поставки | Что создаётся, настраивается, передаётся и документируется |
| Проверка и приёмка | Кто, где и по каким критериям оценивает выполнение |
| Изменения и приложения | Как фиксируются решения и какие материалы входят в согласованную редакцию |

Если проект предусматривает применение ГОСТ, необходимо отдельно определить применимые документы, их редакции и требования к составу ТЗ. Наличие привычных названий разделов само по себе не подтверждает соответствие стандарту.

## 5. Записать требования так, чтобы их можно было проверить

Удобная основа формулировки: **условие — субъект — действие — наблюдаемый результат — ограничение**. Не все элементы обязательно помещать в одно предложение: общую среду или определения можно задать отдельным разделом и использовать ссылки.

Сформулированное требование следует проверить на однозначность, полноту, непротиворечивость и реализуемость. Отдельный идентификатор позволяет обсуждать его без пересказа текста, назначать приоритет и связывать с проверкой. Подход к оценке качества требований рассмотрен в [статье Юлии Новиковой](https://habr.com/ru/articles/825458/).

| Неопределённая формулировка | Что требуется уточнить |
| --- | --- |
| «Отчёт формируется быстро» | Начало и конец измерения, объём данных, нагрузку, среду и допустимое время |
| «Интерфейс должен быть удобным» | Пользовательскую задачу, условия выполнения и процедуру оценки |
| «Поддерживаются все форматы» | Закрытый перечень форматов и ограничения обработки |
| «Предусмотрена надёжная защита» | Угрозы, роли, разрешённые действия и проверяемые механизмы |
| «Ошибки обрабатываются корректно» | Виды ошибок, состояние данных и сообщения пользователю |

Число без условий измерения тоже неоднозначно. Требование ответа «за две секунды» не объясняет, относится ли оно к единичной операции или ко всем запросам, включает ли сеть и при какой нагрузке проверяется.

Атомарность означает возможность независимо управлять обязательством и оценивать его выполнение. Наличие союза «и» само по себе не доказывает необходимость разделения: условие и результат одной операции могут составлять единое требование.

### Карточка требования

| Поле | Содержание |
| --- | --- |
| Идентификатор | Постоянное обозначение, например FR-REG-01 |
| Формулировка | Обязательное поведение или характеристика |
| Источник и основание | Кто подтвердил потребность и зачем она нужна |
| Приоритет и поставка | Значимость и согласованный этап реализации |
| Условия и ограничения | Роль, состояние объекта, среда, диапазоны значений |
| Критерий проверки | Наблюдаемый признак выполнения |
| Связи | Модель, интерфейс, тест и зависимые требования |
| Статус | Черновик, согласовано, изменено или исключено |

## 6. Разобрать требование на примере АС «АЛЬФА»

Следующий фрагмент специально подготовлен для статьи. Значения условные и требуют согласования в реальном проекте; это не отчёт о выполненных испытаниях.

**Задача:** зарегистрировать обращение с темой и описанием. Автором считается пользователь текущей сеансовой записи. Статус после успешной регистрации — «Зарегистрировано».

| Идентификатор | Требование |
| --- | --- |
| FR-REG-01 | При отправке формы авторизованным пользователем система должна проверить тему и описание до создания обращения |
| DR-REG-01 | Тема должна содержать от 1 до 120 символов после удаления начальных и конечных пробелов; описание — от 1 до 4 000 символов после такой же обработки. Для этой проверки символом считается кодовая точка Unicode |
| FR-REG-02 | Если хотя бы одно поле нарушает DR-REG-01, система должна сохранить введённые значения в форме и показать сообщение рядом с соответствующим полем; обращение не создаётся |
| FR-REG-03 | Если оба поля соответствуют DR-REG-01, система должна создать одно обращение, присвоить ему уникальный идентификатор, автора текущего сеанса, время регистрации и статус «Зарегистрировано» |
| FR-REG-04 | После успешного создания система должна показать идентификатор обращения и предоставить переход к его карточке |

У такого фрагмента остаются вопросы: что происходит при повторной отправке, истечении сеанса и недоступности базы данных; допускаются ли вложения; какие правила действуют для разметки текста. До включения соответствующих функций в поставку необходимо определить поведение и дополнительные проверки.

### Связать требования с тестами

| Проверка | Исходные данные | Ожидаемый результат |
| --- | --- | --- |
| T-REG-01 | Тема «Замена оборудования», непустое описание; авторизованный пользователь | Создано одно обращение с идентификатором, автором и требуемым статусом; доступна карточка |
| T-REG-02 | Тема состоит из пробелов | Новое обращение отсутствует; у темы показано сообщение; введённые значения сохранены |
| T-REG-03 | Тема из 120 и затем из 121 кодовой точки без краевых пробелов | В первом случае ограничение темы выполнено, во втором регистрация отклонена |
| T-REG-04 | Пустое описание при заполненной теме | Обращение не создано; сообщение относится к описанию |

Дополнительно проверяются границы длины описания и обработка краевых пробелов. Для каждого теста фиксируются предусловия, действия и способ проверки сохранённых данных. Таблица задаёт ожидаемое поведение; фактический результат заполняется после запуска.

Связи требований и испытаний подробнее разобраны в [материале о трассируемости](/alsibir-expert/blog/analytics/06_requirements_to_tests/).

## 7. Описать данные, интерфейсы и условия работы

Описание функции необходимо сопоставить с моделью данных и интерфейсом. Если в форме используется обязательный справочник, ТЗ должно объяснять его источник и поведение при отсутствии подходящего значения.

Для API — программного интерфейса взаимодействия — следует определить операции, структуру запросов и ответов, правила авторизации, ошибки и поведение повторных запросов. Для импорта нужны формат, правила проверки, обработка неполных записей и отчёт о результате.

| Направление | Контрольный вопрос |
| --- | --- |
| Доступ | Может ли пользователь увидеть или изменить чужое обращение? |
| Ошибки | Что сохраняется при прерывании операции? |
| Производительность | Какой набор операций и данных используется при измерении? |
| Восстановление | Какие данные требуется восстановить и как подтвердить результат? |
| Совместимость | Какие версии среды входят в проверяемую конфигурацию? |
| Эксплуатация | Кто получает журналы, инструкции и средства настройки? |

Архитектурное решение следует закреплять как ограничение, когда для него есть основание: совместимость, инфраструктура или согласованное решение проекта. Если основание отсутствует, полезнее сначала описать требуемый результат и обсудить способы реализации с Разработчиком.

## 8. Добавить модели и примеры с определённым статусом

Схема процесса помогает увидеть участников и развилки; диаграмма состояний — допустимые переходы; модель данных — сущности и связи; прототип — состав экрана. Для каждого приложения необходимо указать версию и определить, какие его элементы обязательны.

Референс следует сопровождать пояснением: что именно требуется использовать и какие особенности не входят в ожидания. Ссылка на чужой сайт без такого пояснения оставляет слишком много вариантов трактовки. Значение примеров, аудитории и визуальных пояснений рассмотрено в [материале Kwork](https://blog.kwork.ru/kak-sdelat/kak-sostavit-idealnoe-tz-chtoby-poluchit-zhelaemoe).

Для проверки согласованности удобно пройти один сценарий через все представления: требование, процесс, экран, запрос, сохранённые данные и тест. Названия ролей, полей и состояний должны совпадать либо иметь явно заданное соответствие.

[Графические модели АС «АЛЬФА»](/alsibir-expert/wiki/portfolio/analytics/alpha-graphic-models/) показывают такое описание системы с нескольких сторон.

## 9. Согласовать приёмку и порядок изменений

До начала реализации необходимо установить состав передаваемого результата, проверяемую конфигурацию, участников проверки и способ регистрации замечаний. Требуется различать запланированные проверки и доказательства фактического выполнения.

Вопросы совместной проверки документа, этапов и согласования рассмотрены в [публикации СберБизнес Live](https://sberbusiness.live/publications/tehnicheskoe-zadanie-kak-ego-sostavit-chtobi-rezultat-opravdal-ozhidaniya). В проекте следует отдельно назначить ответственных за содержание требований, техническую реализуемость, проверку и утверждение редакции.

Для изменения согласованного ТЗ удобно применять следующий порядок:

1. Зарегистрировать предложение с причиной и перечнем затронутых требований.
2. Оценить влияние на функции, данные, интерфейсы, испытания, документы, сроки и ресурсы.
3. Зафиксировать решение уполномоченных участников и состав изменения.
4. Выпустить новую редакцию с историей изменений.
5. Обновить связанные модели, задачи и проверки.

Например, добавление вложений к обращению затрагивает форму, API, хранение, ограничения размера, права доступа и испытания. Одной строки «добавить загрузку файлов» для согласования такого изменения недостаточно.

## 10. Проверить ТЗ перед передачей в работу

Совместное чтение позволяет обнаружить вопросы, которые Автор документа уже перестал замечать. Заказчик проверяет смысл и границы, Разработчик — реализуемость и зависимости, специалист по испытаниям — наблюдаемость результата. Такой подход к анализу и доработке ТЗ описан также в [материале KEDU](https://kedu.ru/press-center/articles/info-it-idealnoe-tz-kak-pisat-chitat-i-analizirovat-tekhnicheskie-zadaniya-bez-oshibok/).

- [ ] Цель связана с конкретной проблемой и ожидаемым изменением процесса.
- [ ] Перечислены роли, внешние участники и границы поставки.
- [ ] Для неизвестных сведений назначены ответственные и сроки уточнения.
- [ ] Требования имеют идентификаторы и согласованные приоритеты.
- [ ] Термины одинаково используются в тексте, таблицах и схемах.
- [ ] Описаны успешные действия, ошибки и значимые граничные условия.
- [ ] Численные показатели сопровождаются условиями измерения.
- [ ] Согласованы данные, интерфейсы и зависимости от внешних систем.
- [ ] Для каждого обязательного требования определён способ проверки.
- [ ] Указаны состав передачи, редакции приложений и порядок изменения документа.
- [ ] Зафиксировано решение о готовности ТЗ уполномоченными участниками.

Практическая проверка готовности: Разработчик может объяснить, что требуется реализовать, специалист по испытаниям — как это проверить, а Заказчик — почему результат решает исходную задачу. Расхождения следует устранить в документе и связанных материалах до зависимых от них работ.

## Источники и дополнительное чтение

1. Юлия Новикова. «Как написать хорошее ТЗ?» — [Хабр](https://habr.com/ru/articles/825458/), [публикация на vc.ru](https://vc.ru/education/1268751-kak-napisat-horoshee-tz). Один авторский материал на двух площадках; критерии качества требований.

3. Kwork. [«Как составить идеальное ТЗ, чтобы получить желаемое»](https://blog.kwork.ru/kak-sdelat/kak-sostavit-idealnoe-tz-chtoby-poluchit-zhelaemoe) — цель, аудитория, примеры и пояснения к ожидаемому результату.
4. KEDU. [«Идеальное ТЗ: как писать, читать и анализировать технические задания без ошибок»](https://kedu.ru/press-center/articles/info-it-idealnoe-tz-kak-pisat-chitat-i-analizirovat-tekhnicheskie-zadaniya-bez-oshibok/) — чтение, анализ и доработка требований.
